# Incremental Learning in a Federated Setup for Health IoT Devices

BTP project, LNMIIT. Aditya Sharma, Hussain Haidary, Dhruv Sangal, Sarrah Sadriwala.

Sports activity recognition from body pose (Penn Action, 14 classes). Everything is reached from one address: a single sign-in page sends the admin to the aggregation console and each client operator to their own node. The pose comes from the camera or an uploaded video and is extracted in the browser with MediaPipe. Three client nodes each run a Bi-LSTM with attention. They learn incrementally from their users' labels (a buffer of 16 windows, replay and EWC) and train together with federated learning (FedProx on the clients, FedAdam on the server, Ditto personal models). The server measures how much each client contributed to every new global model: its update share, its alignment and its exact Shapley value.

```
 browser (camera / .mp4)                     client node k (FastAPI, NumPy)                 server (FastAPI, NumPy)
 MediaPipe Pose → 33 landmarks ──WS──►  46 features/frame → window of 48 → Bi-LSTM+attn
 skeleton + activity label    ◄──WS──   prediction (personal + global model)
 "teach" buttons              ──WS──►  16 labelled windows → incremental step (replay+EWC+Ditto)
                                        heartbeat every 3 s  ───────────────────────────►  round control, users, roles
                                        global model         ◄───────────────────────────  w_t
                                        FedProx local training, upload w_k  ─────────────►  Δ = Σ p_k (w_k − w_t)
                                                                                           FedAdam step, shares, Shapley
 admin + client pages  ◄─────────────────────────── live WebSocket feed of every aggregation step ──┘
```

## One address, separate nodes

`portal/main.py` serves the sign-in page and the aggregation server at `/`, and mounts the three client nodes at `/node/1/`, `/node/2/` and `/node/3/`. Each node is its own copy of `node/main.py` with its own models, data partition, labelled buffer and training thread, and it talks to the server only through the server's HTTP API (`/fl/heartbeat`, `/fl/global`, `/fl/update`), exactly as it would from another machine. The same code still runs as four separate services (`ROLE=server` / `ROLE=node` in the Dockerfile) when the nodes really are on different devices.

| Sign in as | Opens |
|---|---|
| `admin` | aggregation console (`/admin`) |
| `client1`, `client2`, `client3` | that client node (`/node/1/` …) |
| `viewer` | the console read-only, with links to every node |

## What is where

| Folder | Contents |
|---|---|
| `kaggle/` | Training notebook `btp_train.ipynb` (generated by `make_notebook.py` from `pipeline.py`, `extract.py` and `btpcore/`). Runs on a Kaggle GPU, writes `outputs.zip`. |
| `btpcore/` | Feature extraction, the NumPy model with full backprop (checked against PyTorch), learning utilities, and the FedAvg/FedAdam aggregation with contribution measures. Shared by the notebook, the server and the nodes, so the report and the live system use the same code. |
| `portal/` | Single-address entry point: server plus three mounted client nodes. |
| `server/` | Aggregation server: users and roles, rounds, FedAdam, Shapley values, admin console. |
| `node/` | Client node: live prediction over a WebSocket, incremental learning, federated client. |
| `web/` | Sign-in portal (`web/portal`), admin console (`web/admin`), client page (`web/client`), shared layout, JS and CSS. |
| `models/` | Kaggle results, installed with `scripts/install_outputs.py`. |

The whole system runs in one process of about 250 MB (under 400 MB at the peak of a round) with no PyTorch, so it fits the 512 MB free tier on Render or an old laptop.

## 1. Train on Kaggle

1. Upload `kaggle/btp_train.ipynb` to Kaggle (New Notebook, then File, then Import Notebook).
2. Settings: Accelerator **GPU T4 x2** (or P100), Internet **on**.
3. Run all. The notebook downloads Penn Action from its official page. If that fails, add the Penn Action dataset with "Add Data" and run it again.
4. Download `/kaggle/working/outputs.zip` from the Output panel.

## 2. Install the results

```bash
python scripts/install_outputs.py ~/Downloads/outputs.zip
git add models && git commit -m "Add trained models" && git push
```

`models/` receives the weights and node data. `report/` receives the figures, `tables/report_tables.md` (including the comparison with published results) and `params.json` with every hyperparameter.

## 3. Run on one computer

```bash
pip install -r requirements.txt
bash scripts/run_local.sh            # or: docker compose up --build
```

Open http://localhost:8000 and sign in (`admin` / `admin123`, `client1`..`client3` / `demo123`). The camera works on `localhost` and on `https://` addresses only (a browser rule).

## 4. Deploy on Render (free)

1. In Render: New, then **Blueprint**, then choose this repository. `render.yaml` creates one service, `btp-fedhar-portal`.
2. When Render asks, set `ADMIN_PASSWORD` and `DEMO_PASSWORD`.
3. Open the service's address. That single link is the whole system.

A free service sleeps after 15 minutes without traffic, and the first request then takes about a minute. Open the link a minute before a demo. Disks on the free plan are not kept between restarts, so a restart puts the global model and the users back to their deployed state.

## Running a demo

1. **Client pages:** sign in as `clientK` on the portal, choose **Use camera** or **Upload a video**. The skeleton is drawn live. The activity label and the top 3 come from this node's personal model, with the global model's opinion beside it.
2. **Teach:** if the label is wrong, choose the scope (last 3 s, last 6 s or the whole clip) and click the right class. After 16 windows the personal model takes one incremental step. The card shows the loss terms (cross-entropy + Ditto + EWC) and the batch accuracy before and after.
3. **Admin console:** press **Start a round**. Every online node downloads the global model, trains it locally with FedProx and uploads its weights. On both the admin console and every client page you can follow:
   - the five aggregation steps: updates received, data weights p_k = n_k/N, weighted sum Δ, the FedAdam step and the new model;
   - one weight, `out_b[0]`, followed through every step with the real numbers;
   - each client's contribution: share ⟨c_k, Δ⟩/‖Δ‖² (the shares sum to 1), alignment cos(d_k, Δ), exact Shapley value on the server validation set, leave-one-out, and per-layer shares.
4. **Numbers sent and received:** the client page's "Sent to the server" and "Received from the server" cards and the admin console's "Numbers exchanged" table show the size of each transfer and the first values of three tensors. The same values can be matched on both sides.

## Roles

| Role | Can |
|---|---|
| admin | everything: start rounds, change settings (FedAdam/FedAvg, η, μ, Ditto λ, local steps, timeout, automatic rounds, Shapley on or off), manage users, read the audit trail |
| operator | one per node: use its client page and teach its personal model |
| viewer | watch every page, change nothing |

Tokens are JWT (HS256) signed with `JWT_SECRET`, so one sign-in works for the console and every node. Passwords are hashed with scrypt. Nodes authenticate to the server with an HMAC token derived from the same secret.

## Environment variables

| Variable | Where | Default |
|---|---|---|
| `JWT_SECRET` | all | `dev-secret-change-me` |
| `SERVER_URL`, `SERVER_PUBLIC_URL`, `NODE_ID` | separate-node mode only (the portal sets them itself) | |
| `MALLOC_ARENA_MAX` | portal, keeps memory low | `2` |
| `ADMIN_PASSWORD`, `DEMO_PASSWORD` | server | `admin123`, `demo123` |
| `STEP_DELAY` | server, pause between live aggregation steps in seconds | `1.2` |
| `LOCAL_STEPS`, `ROUND_TIMEOUT` | server | `12`, `240` |
| `SERVER_VAL_WINDOWS` | server, validation windows used for Shapley | `240` |
